# 同一应用的两类变更审查

目标用户、代理语料和应用边界沿用 `business_scope.md`。两个流程共享版本证据服务、提交身份、任务保存、回归记录绑定和人工处置；不执行提交代码，不自动批准变更。

## 现有流程：依赖升级

应用提交 A → v2.9.1 到 v3.0.0 静态预审 → 修改产生提交 B → 同规则对照审查 → 关联 B 的外部回归记录 → 人工处置。风险消失只表示本轮未观察到，旧提交的测试不能为新提交背书。旧结果读取、修改后复查、调用层缺失构成三个验收路径。

## 新流程：配置变更

当前支持同一应用、PaddleOCR v2.9.1 的显式 `drop_score` 数值变化：直接数值、唯一常量、明确的普通函数实参，以及已提交 JSON/YAML 的受限读取链。比较两份应用快照，定位参数及数值来源，查询相同依赖版本的参数定义，解释过滤行为变化，核对应用契约，生成比较回归要求，再关联候选提交的记录。

配置文件必须以调用中原样出现的项目相对标签提交；系统不猜运行工作目录，不读取任意磁盘文件，不执行应用。闭包、参数遮蔽、别名或容器变更、动态覆盖等无法明确解析时保留缺口。静态声明可解析不等于配置实际加载或生效，共享数值的其他用途也须单独检查。

- 提高阈值可能使原来保留的低分文字被过滤；这是行为变化，不能直接认定缺陷或识别精度提升。
- 动态参数、环境变量、字典展开、无法确定的绑定和缺失调用层形成缺口；不假定配置已经生效。
- 如果还有阈值以外的代码或文件变更，保留额外审查缺口；初版不把参数检查当成整次变更安全证明。
- 验收需覆盖阈值两侧、等于阈值、空页和多页；检查文本、页序及 JSON 契约。固定分数夹具只验证过滤边界与输出逻辑，不能证明真实 OCR 质量。
- 代码片段/原创案例标记临时诊断；正式输入使用登记应用的基准与候选 Git 提交。依赖版本在此流程中保持不变。

## RAG 收尾

保留十五题的逐题事实、来源和缺口清单，区分检索证据覆盖、生成事实支持和回答完整性。先补检索，只有生成上下文出现新的有效来源内容才再次生成。同一来源中的新窗口也算新证据；仅排序变化不算。核验器不能同时引用主张又说该要点完全未回答；此类判定保留为意见冲突，不能自动抬为答全或误标为资料不存在。

## 共用验收要求

报告区分：静态已知、待处理事项、未验证运行。记录绑定工作流类型、应用、基准/候选提交、文件哈希、依赖版本、语料和报告；夹具、人工日志与可信 CI 认证分别描述。公网导入记录只认作未认证的人工记录。改输入后不得复用旧处置或测试。

本次不新增通用 Agent 框架、自动修代码、任意仓库接入、在线执行或自动发布能力。
