# 内部 OCR 维护主线收敛与验收

本轮依据 `business_scope.md` 与 `business_baseline.md`，维护同公司 OCR 封装及内部应用；PaddleOCR 依赖版本不冒充公司 SDK 发行版本。未推送 GitHub 或更新公网。

## 实际改动

1. 内部任务新增 `workflow_type`。升级为 2.9.1→3.0.0，配置固定 2.9.1→2.9.1；类型、快照、版本进入幂等身份。配置必须提供基准提交，不允许无必要的模型建议。
2. 配置接入既有 API、持久任务、Worker、取消、租约、权限和构建身份检查，不另建队列。
3. CI 声明绑定目标版本、提交、输入哈希、当前报告。独立审核者需逐项说明接受风险或配置行为变化的理由；最新失败运行覆盖旧成功。可信来源不自动证明测试充分，也不自动批准发布。
4. 内部页面说明两个目的和各自提交要求；配置结果复用配置报告组件，不再套用“未发现升级风险”。企业身份仍需部署方真实接入，本地 JWT 测试不等于完成企业部署。
5. RAG 修复：阈值边界优先保留比较分支；补齐有界源码循环/条件；参数表保留表头与命中上下文，去掉中间无关行。区分批处理与数值边界；多问句里的明确组件不被父 OCR 范围覆盖，回归覆盖当前九种组件。
6. 验收脚本为配置生成真实基准、候选和开发者调整提交，验证复查及跨提交旧记录失效；新增原文上下文对照。开发运行器可显式覆盖 2.9.1 的 drop_score，并注明不证明应用配置加载机制。

## 资料审计

本轮没有盲目扩大官方语料。阈值比较和旧参数转发源码已经收录，实际问题是检索选择和上下文组织。来源身份、两个固定提交和上游原文保持不变。

新版字段逐项对应的直接实现依据仍有限：PaddleOCR 将部分实现委托给 PaddleX，不能把任意版本 PaddleX 源码标为 PaddleOCR 3.0.0 的无条件保证。后续补充需先冻结实际 PaddleX 依赖、区分发布者及组件版本，并重跑评测。应用自己的 JSON 契约和运行记录不能由官方说明代替。

## 真实 OCR 观察

相同三张原创合成扫描页（两张带文字、一张空白）、固定本机环境：

- 旧应用提交 `b1c7a1de25bc7bc5bacc83ecdb95cd243f3943e3` 在 PaddleOCR 2.9.1 / PaddlePaddle 2.6.2 的实际应用入口通过。
- 同一提交换成 PaddleOCR 3.0.0 / PaddlePaddle 3.0.0 / PaddleX 3.0.0，入口出现 `IndexError`；独立适配器探测成功没有覆盖入口失败。
- 字段适配提交 `f4829a5795f2d439cac39bd55dc6ece9b84bdc72` 在同一 3.0.0 环境通过这组样本的入口、文本片段与 JSON 契约检查。三份记录确认工作区干净。
- 配置提交 `f52eb1f66ea3dbbd5e26573b810439679c661d2b`（0.5）及 `4296613e9c5c42d3e0796919f1bb4cb46bf3e309`（0.8）使用相同输入，入口契约均通过，未观察到 JSON 文本变化。样本清晰，不能推断门槛不影响低分文字；阈值边界由固定分数夹具另测。

配置采用运行器显式参数，经原创调用封装进入应用，未证明配置覆盖/加载机制。三张独立扫描页不代表所有多页 PDF 或识别准确率。新版服务器模型在本机 CPU 的推理耗时为数分钟，不能与 RAG 回答延迟混为一谈。

## RAG 实验口径

原始记录位于忽略目录 `.local-demo-temp/convergence-20261025/`，包含问题、响应、来源、语料/源码/策略身份及耗时。不同目录代表不同阶段，不能拼成最终成绩。

| 目录 | 用途 |
|---|---|
| retrieval-before | 49 个已知业务问题的只检索基线；成功响应不等于事实检全 |
| generated-before | 8 题定位性生成验收 |
| generated-after | 中间版本 49 题：30 题模型完整、15 题部分支持、4 题未评完整性；不是人工准确率 |
| context-probe | 同一批检索来源的短窗口/有界完整块对照；没有额外来源或参考答案，不叫 gold-context 准确率 |
| strategy-comparison / strategy-final | 保留中间代码身份的策略实验 |
| generated-final / strategy-verified | 最终代码身份验收，汇总以完整原始结果为准 |

上下文对照中，旧结果迁移题在完整块下由部分支持变为模型判定完整；字段对应与旧参数题仍部分支持。不能只靠增加 Top-k 解决，也不能靠降低核验要求制造全通过。

公平比较以相同结构窗口、候选 80、Top-5 的 BM25 与真实 BGE 混合为主。原始块 BM25 与结构化方案同时改变表示和候选组织，只能作为整体基线比较。题集属于已知开发/回归资料，不是独立专家盲测。源码字面事实命中、引用支持、回答完整性和人工正确性分别报告。本机同时有测试任务，计时是运行观察，不是独立生产压测。

最终四策略对照（同一冻结的 12 题）：

| 策略 | 所需字面源码事实完整命中 | 检索中位耗时 | 不符题目模块的结果条数 |
|---|---:|---:|---:|
| 原始块 BM25 整体基线 | 2/12 | 5.35 ms | 41 |
| 结构化 BM25 + 多查询排名融合 | 11/12 | 13.40 ms | 7 |
| 同结构窗口的 BGE 混合 | 10/12 | 34.13 ms | 9 |
| BGE 混合 + BGE 重排 | 11/12 | 24,709 ms | 3 |

四种策略均实际执行 12 题，未以回退 BM25 冒充神经模型成功，未返回错版本。所有比较仍有干扰结果；结构化 BM25 的 11/12 不代表所有引用都相关，更不代表回答准确率。混合未提高这组完整事实命中，重排减少模块干扰但在本机 CPU 显著变慢，本轮保留结构化 BM25 为默认，不因面试包装强推混合。

最终 49 题生成验收身份一致、请求错误 0、版本范围异常 0；28 题模型判定完整、17 题部分支持、4 题未评完整性（包含澄清/范围边界）。中位 7.109 秒、最长 17.547 秒。此结果只代表该次运行，生成存在波动，独立人工准确率仍为空。

尚未关闭的 RAG 问题分开处理：缺应用资料时的边界回答；旧版多要点证据被不合适来源占位；源码链推导未被生成器稳定表达；字段对应的直接依据不足；核验器对问题背景增加了不必要义务。不能把这些全部解释成“语料太少”，也不能通过更多拒答或修改计分规则消除。

## 验收矩阵与边界

| 项目 | 检查入口 | 验收要求 |
|---|---|---|
| 两流程统一任务 | internal_api / internal_worker / internal_workflows | 类型、双提交、版本、身份不串用 |
| 记录与人工处理 | internal_records | 错版本、旧提交、错报告或较新失败不能背书 |
| 查询范围 | query_plan / EvidenceSearch | 前置范围过滤，多问句/明确组件不混淆 |
| 上下文与引用 | context_selection / retrieval_views | 扩展仍来自同一原文，保留哈希与行号 |
| 页面 | internal_workbench / configuration_workbench | 展示动作和未知，读取不重新执行任务 |
| 回归 | maintenance_acceptance_v1 / 原创运行器 | 保存真实成功与失败，关联提交、样本、环境 |

未宣称完成：独立业务专家验收、真实企业试点、企业 IdP/受控 CI 部署、生产备份恢复和并发压测、所有真实文档及配置加载路径。模型存在波动，部分支持与资料缺口继续显示，不能改成全通过。
