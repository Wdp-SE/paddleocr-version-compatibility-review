# 内部SDK维护与变更审查业务基准说明

更新日期：2026-10-25。

本轮实现及实际验收见[维护主线收敛记录](maintenance/2026-10-25-convergence-verification.md)。其中区分静态查证、真实本机 OCR、模型判定及未完成的企业部署验收。

本文供项目维护者、后续协作AI及项目介绍使用，明确业务目标、角色、对象、实现对应关系和验收方式。固定业务边界以 `business_scope.md` 为总则；本文细化其内部SDK维护语境，不能把目标能力当作已经完成的功能。本文依据本地工作区代码和既有记录编写，不代表本轮重新验收或公网已更新。

## 一 业务结论与项目目标

本项目面向公司内部研发工程师、测试人员和应用负责人，支持内部OCR调用封装及相关应用的维护：按适用版本查资料，在上线前审查升级和配置变化的影响，形成有依据的处理事项，并关联复查与回归记录。所有调用方均处于同一公司内部。这里的“消费者”是使用封装输出的内部代码模块，不是购买SDK的外部客户。

业务目标可以表述为“内部SDK维护与变更影响审查”。当前学生POC使用PaddleOCR真实开源资料代理内部组件版本知识，使用原创扫描文档应用代理内部维护任务。PaddleOCR的发布者始终是PaddlePaddle；不能把公开资料改名成企业私有文档，不能声称已经有企业用户或生产收益。

目标与实现之间有一处必须保留的差距：当前登记和审查的单位是一个内部应用的代码快照，其中包含OCR调用、结果适配、归一化和JSON输出。它模拟内部SDK或组件封装的职责，但尚未独立发布为具有单独版本、包名和多应用使用历史的内部SDK产品。现有实现没有覆盖任意内部SDK自身接口、类型和实现变化的通用兼容性比较。

当前明确支持两条流程：底层依赖由PaddleOCR v2.9.1升级至v3.0.0；依赖保持v2.9.1时，比较显式drop_score数值配置变化。两条流程服务于同一个内部应用，不扩大为外部SDK客户支持、任意仓库自动修复或通用企业知识平台。

项目要验证的价值是：维护者能否更完整地找到适用依据、定位受支持的使用位置、识别缺口，并将处理与测试对应到明确提交。减少耗时、减少遗漏、提高准确性属于需要对照实测的收益假设，不是既有成果。

## 二 三类对象及其关系

| 对象 | 业务中是什么 | 当前实现与资料身份 |
| --- | --- | --- |
| 底层OCR依赖 | 内部封装使用的OCR引擎及其版本契约 | PaddleOCR官方固定版本文档、代码和配置；真实公开资料 |
| 内部SDK或OCR组件封装 | 公司维护的调用、适配和统一输出能力，隔离底层差异 | 原创应用中的ocr_client、normalizer、result_adapter等职责；未独立发包 |
| 内部使用方 | 调用封装、接收标准输出并完成内部处理的应用或模块 | 原创pipeline与consumer；实际使用和契约必须从提交文件读取 |

同一应用内的逻辑边界允许以模块呈现，不要求为了演示拆成多个服务。当前调用链为：application.pipeline.process调用ocr_client.recognize，取得原始OCR结果后进入normalizer及result_adapter，再由consumer.to_json形成输出。升级风险可以位于封装内部，消费者未必需要修改。

理想情况下，封装适配完成后，内部应用继续使用稳定输出。如果所有消费者始终正确使用统一契约，底层结果结构变化应由适配层吸收；不能为了显示风险，刻意让所有业务代码直接读取PaddleOCR原始结构。

需分别记录三条版本轴：

| 版本轴 | 表示什么 | 当前可用标识 |
| --- | --- | --- |
| 上游依赖版本 | 官方接口与行为适用范围 | v2.9.1和v3.0.0，不能解释为公司SDK版本 |
| 内部SDK版本或快照 | 公司封装自身代码与输出契约 | 目前随应用Git快照管理，未登记独立SDK发行版本 |
| 内部应用版本或快照 | 具体维护任务对应的基准与候选代码 | 已登记仓库的不可变Git提交；未编造内部版本号 |

后续如果独立SDK化，必须新增真实包边界、导出接口、SDK快照与使用方登记，再验证相关能力；仅改页面名称不算完成。

## 三 业务问题与责任分工

真实维护问题不是“公司先不审查直接上线，再找哪里坏了”。本系统位于变更提出后、合并或发布前；失败案例用于预审和验证，不代表鼓励生产试错。

研发人员提出升级或配置变更，提供明确快照与目标。系统核对支持范围、应用事实和版本依据，输出可处理事项。开发者在受控环境修改；测试人员运行回归；负责人依据组织流程决定继续、延期或拒绝变更。

| 角色 | 主要输入与操作 | 责任边界 |
| --- | --- | --- |
| SDK或组件维护者 | 提供变更目标、调用封装、适配逻辑及组件契约 | 保证组件资料和变更内容可追溯，处理适配问题 |
| 内部应用维护者 | 提供实际使用位置、输出需求、应用快照 | 确认哪些消费逻辑存在，不能由官方文档替代 |
| 测试人员 | 提供样本、测试定义、实际环境与运行记录 | 区分夹具和真实推理，确认测试覆盖要求 |
| 应用负责人或审核人 | 查看当前报告、缺口和对应回归，记录处置理由 | 接受或拒绝业务风险；系统不代替发布审批 |
| RAG与受控编排 | 检索、静态核查、组织证据和处理事项 | 显式保留未知项，不执行待审代码或自动批准 |

该场景更适合版本资料分散、维护交接较多、需要保留审查依据的团队。对于偶尔修改一次的极小封装，人工看迁移说明加已有测试可能更划算。单一参数变化也不必调用模型；确定性规则能够完成的步骤优先由程序完成。

## 四 为什么外部资料不能直接证明内部需求

PaddleOCR外部使用者和公司内部SDK维护者不是同一用户画像。外部反馈只能证明某类接口或运行问题确实可能发生，不能证明某家公司有相同流程、内部契约、维护频率或采购需求。

内部SDK维护仍可能需要处理上游依赖变化，但内部封装应承担隔离差异的职责。内部使用方是公司内的应用团队或模块。由SDK维护者发起升级、系统检查封装及内部使用位置，比“替外部客户审查PaddleOCR”更符合本项目边界。

公开研究与实践分四层解释：

| 证据 | 能支持什么 | 不能支持什么 |
| --- | --- | --- |
| PaddleOCR官方升级说明 | 2.x到3.x存在真实非兼容变化 | 不能证明公司内部SDK具有相同接口或已发生事故 |
| Adevinta的PaddleOCR工程实践 | 企业会封装开源OCR，并需要读文档、配置与源码 | 不能证明其使用我们的工作流或经历本演示升级 |
| Monzo的内部库迁移实践 | 内部封装、调用位置迁移、自动化与人工处理有现实依据 | 大规模迁移收益不能直接套到一个应用 |
| 当前POC与对照实验 | 某个固定案例能否被发现和正确处理 | 不能自动推导企业ROI、用户覆盖或生产可用性 |

当前没有企业访谈、真实内部SDK资料或组织试用记录。因此业务问题有公开依据，具体产品适配与收益仍待验证。现有编码Agent也能辅助依赖迁移，不能再把“其他工具只能改版本号”作为产品优势。

## 五 统一知识服务的具体实现

RAG服务同时供人工查询和两条工作流查证。人工可以问当前依赖用法；工作流按核查点请求对应版本的组件证据和当前应用资料。两者共用服务，但官方资料和应用资料的身份、范围及权威性不同。

当前官方活动语料清单记录62条来源、1794个原文块，包括Markdown、Python与YAML。这是该工作区资料规模，不是企业完整资料覆盖率。原创应用资料按本次提交独立检索，不混入官方组件索引。

主要过程如下：

1. 识别问题范围与明确版本。查询与版本选择冲突时先澄清，不用其他版本填补答案。
2. 在对应资料范围中使用BM25等已配置策略检索。多查询是同一问题的多个检索表达；RRF用于融合多个排名，不代表已经使用向量混合检索。
3. 按结构保留参数定义、函数、调用示例和必要上下文。多点问题分别检查必要事实，而非只保留相似度最高的一段。
4. 组装有来源、版本、提交、哈希及行号的证据。来源真实不等于与当前主张相关。
5. 生成回答或建议，校验引用身份与原文支持。模型自检不是人工准确率认证。
6. 缺关键事实时有界补查。只有实际新增有效上下文时才再次生成；仍不足则返回已有依据和具体缺口。

组件资料能解释“新结果如何访问”，应用contract.json才能说明“我们的JSON必须有哪些字段、如何保留空页”。官方说明不能证明本应用已完成迁移、运行成功或负责人已经批准。

当前入口主要位于versioned-rag-service/src；调用适用性、引用支持与完整性分别处理。历史BGE混合和重排实验不能直接代表当前本地或公网默认策略，必须查看活动配置及其来源、代码指纹。

## 六 流程一 内部OCR封装升级审查

业务触发是维护者计划升级封装底层依赖，希望获得新能力或维护支持，同时保持约定的内部输出。已实现案例固定PaddleOCR v2.9.1到v3.0.0，发生在上线之前。

正式输入是已登记应用ID、基准和候选提交、当前和目标依赖、变更目的，以及登记范围中的调用、适配、消费者、契约和测试。代码片段仅用于临时诊断，不能代替完整登记上下文。

| 步骤 | 实际执行的工作 | 产出与失败处理 |
| --- | --- | --- |
| 1 固定输入 | 解析服务器登记仓库的Git引用，读取不可变快照 | 提交、文件哈希和收集范围；缺文件或超预算保留缺口 |
| 2 读取应用事实 | 核对依赖文件角色、调用入口、输出字段与分页要求 | 当前与目标依赖分开；契约缺失不能从官方资料补造 |
| 3 静态检查 | AST与规则识别调用、结果读取及受支持的跨函数关系 | 文件行号与规则发现；动态关系保持未知 |
| 4 双版本查证 | 通过RAG核对两版官方契约及实际原文 | 支持风险、未观察到变化或证据不足，不凭模型猜测 |
| 5 形成处理事项 | 解释哪个位置为何受影响，关联消费者候选和回归要求 | 关系候选不自动升级为已确认受损 |
| 6 修改后复查 | 开发者修改为新提交，系统按同一范围与规则重新审查 | 风险仍存在、未再观察到、增加或因缺口无法判断 |
| 7 关联运行与处置 | 外部环境执行真实回归，绑定新提交、报告和环境 | 运行通过、失败、未验证分别展示，由人决定后续 |

典型风险是适配层继续调用normalize_v2读取旧结构，而升级后应按目标结果访问方式完成转换。检查重心应在封装内部。若统一输出契约保持，consumer.to_json可以不修改；不能把所有内部消费者都说成直接使用旧PaddleOCR结果。

正式检查须包含未修改的相关文件。PR可能只修改依赖或适配器，未修改的消费者仍可能受影响。当前对照是受支持规则和文件级比较，尚不是任意代码语义的完整差异分析。

验收至少包含旧适配风险、改后复查、缺调用层、静态未发现但运行失败、无相关调用五类路径。最后一种应报告本次范围未发现相关使用，不能制造迁移风险。

## 七 流程二 同版本OCR配置变更审查

业务触发是内部维护者调整封装参数，例如希望减少低分文字进入输出，又担心遗漏仍有业务价值的文字。当前仅支持依赖保持v2.9.1、显式PaddleOCR构造器drop_score数值变化，可追踪受限常量、明确普通函数实参和已提交JSON/YAML的数值来源；不宣称覆盖任意配置或故障诊断。文件标签须与读取声明精确一致，静态追踪不证明实际加载。动态覆盖、闭包和绑定歧义继续形成缺口。

正式输入应包含修改前后快照、实际依赖、参数生效位置、内部输出契约、样本与验收目标。验收要求先于测试结果明确，避免看见输出后再改变合格条件。

1. 核对两份快照的当前依赖均固定为v2.9.1。未知、冲突或动态依赖保留缺口。
2. 识别显式参数变化及位置，核对同版本官方定义。动态参数、环境变量和复杂转发不强行判断。
3. 说明过滤行为变化。阈值提高可能减少返回文字，不等于识别模型变准；阈值降低可能引入更多低分结果，也不必然是缺陷。
4. 读取应用契约，列出应比较的输出字段、空页与多页要求。没有提交的内部关键字段要求不能编造。
5. 在开发者环境对相同样本作前后对比，检查阈值两侧与等于边界、文字集合、页序和JSON契约。
6. 将记录绑定候选提交及实际环境，由人记录接受、修改或延期。没有标注答案就不计算业务识别准确率。

当前程序已经实现参数差异、同版本证据和应用契约核对，核心流程不强制模型调用。2026-10-26增加六张原创合成页的真实OCR阈值对照，证明其中两张输出会变化；该实验使用运行参数覆盖，不证明JSON/YAML实际加载、独立SDK配置发行或业务收益。不能把静态desired_check文本当成测试已经完成。

固定分数夹具验证过滤边界与输出逻辑；真实OCR测试观察实际识别与过滤；业务验收判断是否满足内部要求。三个结论不能相互替代。若同时改了依赖或其他不支持的配置，应分流或显式扩大缺口，不按单参数流程给整次变更背书。

## 八 工程分工与数据约束

Streamlit负责操作与结果展示，FastAPI负责知识和受限审查接口，Agent代码组织规则与查证。静态程序负责可确定的事实，模型用于可选解释和查证规划。模型不能关闭规则风险、修改应用契约或改变发布决定。

公开演示与内部部署是不同运行模式。公开演示只接受公开和原创模拟数据，匿名日志属于未认证人工提交；内部模式已有认证、动作权限、持久任务及可信CI来源验证代码，实际IdP、PostgreSQL、受信工作流与部署仍需单独验收。不能笼统说“完全没有权限实现”，也不能说“企业权限已落地”。

| 状态维度 | 需要表达的内容 | 不允许的推断 |
| --- | --- | --- |
| 任务执行 | 排队、运行、失败、取消、完成 | 分析完成不等于升级成功 |
| 事项处理 | 待补资料、待修改、待复查、已有处置 | 记录已读不等于风险已消除 |
| 运行验证 | 未运行、夹具、人工日志、可信CI声明、失效记录 | 有测试文件不等于运行通过；可信来源也不保证覆盖充分 |
| 人工决定 | 确认、延期、继续评审等组织动作 | 继续评审不等于发布批准 |

重复相同输入应返回同一任务；Worker的租约与领取身份限制过期写入；取消后的晚到结果不得覆盖状态。报告和运行记录绑定应用提交、文件、依赖、语料与策略身份。代码或资料变化后，应创建新身份并使旧记录不能为新输入背书。

模型网络失败时保留可用原文及静态发现，明确建议未生成。服务端不自动重试可能已经计费的模型POST；已完成查证复用不等于模型调用恰好一次。界面刷新不应成为重新执行昂贵分析的触发条件。

当前受限Git输入不接受任意仓库URL，最多12个文件、单文件50KB、总计200KB；跨函数分析有六层、200个调用上下文等限制。预算和规则未覆盖的内容必须出现在范围说明中。

## 九 测试与效果验收

本节区分已有代码、历史验证与建议新增验收。本次编写文档未重新运行模型、真实OCR、数据库或公网测试，不报告新的通过率。

先固定应用与代码提交、语料哈希、策略配置、问题集、模型配置和样本身份。开发题用于定位问题，已见题用于回归；独立留出题需由未参与调试的人审阅，不能由同一模型自评后称为盲测。

### RAG验收

| 检查 | 具体方法 | 合格证据 |
| --- | --- | --- |
| 正确证据对照 | 人工选好完整依据直接交给生成器 | 区分检索失败和证据已给但仍答错 |
| 资料与召回 | 标注每题必要事实及可支持原文 | 分别记录语料缺失、候选漏召回与上下文遗漏 |
| 回答事实 | 对照版本、类型、参数与必要要点 | 人工逐项判定正确、遗漏、错误及应澄清情况 |
| 引用与拒答 | 检查引用支持及无关真实来源 | 分别记录无依据回答、误拒答和部分回答 |
| 策略比较 | 同一任务比较BM25、混合与重排候选 | 保留逐题结果、实际耗时和调用成本，变化后重测 |

不能用“返回引用的题数”作为回答准确率；必须注明分母是否包括澄清、范围外和无答案问题。检索覆盖、回答完整、事实正确、引用支持是不同指标。P50与P95需足够请求量并说明环境，单次演示耗时不作为服务承诺。

### 两条流程验收

| 编号 | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| U1 | 旧适配器随依赖升级 | 定位真实读取位置，绑定两版依据及运行要求 |
| U2 | 修改适配器形成新提交 | 原风险对照清楚，旧测试记录拒绝复用 |
| U3 | 缺少调用层或输出契约 | 指明缺口，不输出升级兼容结论 |
| U4 | 静态未发现但实际回归失败 | 仍显示运行失败，不能以静态结果覆盖 |
| U5 | 当前范围没有相关调用 | 不制造风险，保留检查范围与限制 |
| C1 | 同版本提高或降低阈值 | 描述行为变化，不默认判缺陷或质量提升 |
| C2 | 阈值下方、相等及上方 | 与固定版本实际过滤规则一致 |
| C3 | 空页、多页及文字变化 | 对照页序、字段和预先声明的应用要求 |
| C4 | 动态配置或同时更换依赖 | 显式不支持、澄清或分流，不冒充完整核验 |
| E1 | 重复提交和多Worker领取 | 任务去重，只有当前持有者可以写入 |
| E2 | 取消、进程中断和恢复 | 状态可查询，旧Worker与晚到请求不能覆盖 |
| E3 | 非所有者和无审核权限 | 后端拒绝越权操作，不只在页面隐藏 |
| E4 | 旧记录、较新失败或伪造CI身份 | 拒绝错误关联，不继续沿用旧成功 |

测试分五类保存：纯程序单元测试；固定语料集成测试；原创夹具；开发者环境真实OCR；部署环境的身份、数据库及CI验收。每份记录写清实际执行类型与身份，未执行保留NOT_EXECUTED，跳过项不计通过。

## 十 当前能力与差距

| 项目 | 当前事实 | 后续需要验证或补齐 |
| --- | --- | --- |
| 内部SDK边界 | 模块职责能模拟封装，按单应用快照审查 | 若单独发包，补真实SDK身份、导出接口与版本关系 |
| 依赖升级 | 固定两版、静态规则、版本查证和改后对照 | 不宣称通用SDK接口差异或任意使用方完整覆盖 |
| 配置变更 | 单版本显式drop_score规则及契约检查 | 以实际样本对比证明业务意义，不扩大支持范围 |
| RAG效果 | 有历史比较和已见问题复验，复杂组合仍可能部分回答 | 独立事实审阅、替代方案比较及当前身份下重验 |
| 工程能力 | 有任务、租约、身份与CI来源等代码基础 | 真实部署、负载、恢复和组织身份集成不能仅凭单元测试证明 |
| 业务收益 | 个人POC及原创维护案例 | 无真实企业用户、维护频率、节省时间或减少事故的收益证明 |

已有2026-10-19检查记录不能作为2026-10-25全量新成绩。历史记录明确human_accuracy为空，后续定向复验与前轮49题结果也不能拼成同一批当前全量结果。页面和文档中的规模、策略、通过数必须能追溯到同一代码与资料身份。

2026-10-25已修复这一实现断点：内部任务按workflow_type分派，升级目标为3.0.0，配置目标保持2.9.1；可信运行声明及继续人工评审按各自目标校验，配置行为变化也需说明接受理由。本地API、Worker及签名身份集成验收不代表真实企业IdP或CI已部署；生产接入仍需专项验收。

下一轮优先完成RAG失败归因、两条实际闭环和工程异常演练。独立SDK打包只在真实接口边界确有必要时再做，不通过改名或制造版本历史追求表面完整。

## 十一 防止业务漂移的变更准入

新增需求应能回答：谁在什么维护时刻遇到什么问题；是否属于同一内部OCR封装和应用；必要证据在哪里；规则、检索、模型和人工分别承担什么；如何复现成功与失败；维护成本是否值得。答不清时先保持范围，不立即增加功能。

应禁止的混淆包括：将内部使用方说成外部客户；把PaddleOCR版本称为公司SDK版本；将官方资料冒充企业原创；把参数变化默认认定缺陷；把静态无风险、夹具通过或模型自检解释为实际兼容；把公网演示解释为企业生产部署。

未来协作AI须先读取AGENTS.md、business_scope.md和本文，再查看实际代码。提案和材料分别标注业务目标、当前实现、历史记录与待验收能力；不得为了叙事顺畅而省略差距。业务范围需要改变时，由用户明确决定并同步资料、代码、案例及评测，不只修改一处介绍。
