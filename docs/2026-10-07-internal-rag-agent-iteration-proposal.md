# 内部研发知识查询与升级影响审查 POC：迭代建议

日期：2026-10-07。状态：供讨论的优化方案，尚未实施，不代表已获得效果提升。

## 固定范围与成功目标

遵守 business_scope.md：面向内部研发工程师、测试人员和应用负责人；PaddleOCR 开源中文资料、接口代码与配置作为内部知识的代理语料，保留真实来源；原创文档处理应用用于验证维护任务。Agent 聚焦 v2.9.1 → v3.0.0 升级，调用人工问答共用的 RAG。没有真实企业用户、内部生产数据或 ROI 实测。

目标是提高必要事实覆盖、回答有据性、升级风险定位和处置可追溯性。允许增加等待时间，但额外推理步骤必须证明有收益；错版本、无依据的兼容结论、过期回归记录不得用速度收益抵消。

## 已核查的基础

- 58 条版本化来源：44 Markdown、9 Python、5 YAML；1754 原文块。现有类别覆盖检查显示两版安装、接口、用法和配置都有来源，但类别存在不等于事实覆盖充分。
- 原文结构块使用 1800 字符软上限，保留代码、表格、Python 定义与 YAML 顶层映射。派生检索视图有 384 计数预算；部分构建路径以 len 回退，不能统一宣传成真实 384 token。原文块和检索视图大小须分别说明。
- 已有窗口、上下文、40/80/120 候选、BGE/融合/重排实验，不重做全部组合。V4 记录范围窗口与模型重排在 8 条留出上均 7/8；这是小样本必要事实覆盖，不是回答准确率。
- 144 个图片引用未提取；既不等于 144 张独立图片，也不能宣称其内容可回答。
- 补查当前验证来源身份与版本，不保证具体核查问题已被证据回答。审阅记录尚未关联风险处置、外部回归结果及最终升级决定。

## 迭代一：按任务补资料，同时冻结验证规则

制作问题—所需事实—官方来源—适用版本的覆盖表。失败分为：无来源、原文未解析、候选未召回、排序丢失、上下文残缺、生成错误、校验误拒。仅前三类涉及语料或解析补充，其他类不能靠堆文档修复。

已从两版固定 Git tree 发现尚未收录的候选：setup.py、pyproject.toml、requirements.txt，旧版 tests/test_paddleocr_api.py，新版 tests/pipelines/test_ocr.py 等。先核对实际内容及任务关联，再决定导入。测试代码展示上游预期，不能代替内部应用验收；要求项不能被误当成已验证完整环境组合。

保持同一仓库与两版范围，不全量导入训练、模型权重或无关产线。代码里的英文标识符不违反中文业务资料定位。设计说明、输出契约和应用测试只按缺口补充，不另造大量内部资料。图片先确定是否存在任务必需且文本未覆盖的信息，再做小范围抽取试验；识别结果须绑定原图身份、版本及人工核查状态。

拟新增 48 条查询（24 开发、12 验证、12 最终留出），按章节/主题分组，包含准确 API 词、自然语言改写、参数表、多事实问题、跨版本差异、无答案和范围歧义。标注正确事实与原文 span，不只标来源文件。已有题作为回归集，不再当未见数据。

拟新增 24 个应用案例，覆盖有风险、无目标风险及证据不足三类，按代码组织骨架划分数据。逐实例标位置与关系，避免仅统计一个规则类别被命中就宣布全部位置召回。优先由另一位同学独立编写或复核；若仍自标，明确报告这一局限。

## 迭代二：RAG 做有限、有依据的实验

先修版本/产线语境与上下文断裂，不放松证据校验来换取表面回答率。

1. 原文保持不可改写；利用章节、表头、函数签名、配置路径辅助检索，引用仍回到原文。
2. 在同一真实 tokenizer 和重排输入上限下，仅比较 256/384-token 窗口及现有结构边界方案。query 与继承上下文都计入预算，不静默截断。
3. 选好表示后，比较范围 BM25、BM25+重排、语义/关键词 RRF+同一重排器。只有语义改写仍漏召回时才扩大语义方案，不因名称复杂而默认采用。
4. 只对入围方案比较候选池 40/80 与最终证据 5/8；候选覆盖和最终事实覆盖分开。不能把扩大池但仅打分前 40 条称为充分利用扩大池。
5. 对查询中的不同核查点做证据覆盖和去重，避免同一来源高分片段占满所有名额；检索前保留版本硬边界，产线歧义需要澄清或分支检索。
6. 身份核验、事实支持、回答正确性分别记录。证据不足针对缺失核查点定向补查；增加查证轮数必须在验证集证明改善，否则不增加。

主指标：必要事实召回、完整事实覆盖、端到端任务正确率、引用与主张支持、错版本及错产线、无答案正确拒答、可回答问题误拒答。端到端采用明确事实清单人工验收，不只依赖同一模型自评。耗时、实际 token、费用和故障回退同时报，不用几毫秒抵消内容错误。

开发集筛选、验证集选最终方案，再首次打开新留出集报告；留出不用于改词典或选择参数。小样本报告绝对计数与分母，不宣称最优、零幻觉或统计显著。若候选没有稳定改善，保留基线并记录失败。

## 迭代三：Agent 深化同一升级任务

工作流：应用身份与当前依赖 → 版本契约变化 → 定位实际调用 → 追踪已支持的关系 → 逐项 RAG 查证 → 证据充分性判断 → 缺口补查 → 风险及回归任务 → 人工处理 → 导入外部回归记录 → 最终决定。

- 变更请求补齐应用标识、文件哈希、当前/目标依赖、变更目的和验收契约；没有应用发行记录时不编造版本。
- 文件区分调用层、消费者、配置、设计和测试。不调用 OCR 不自动等于缺口；真正缺失的本地引用、解析失败与不适用分别记录。
- 每项查证记录需要验证的事实、各版本证据和剩余未知项。来源真实不等于内容充分，补查状态也不等于风险已解决。
- 影响路径继续区分直接结果流、引用候选和未知动态关系；不把检索相似度升级为业务因果关系。
- 每项风险关联待检查接口/字段、原文依据、应用位置、验证方法和人工处理意见。回归要求针对风险，不只套用带文本/空页/多页同一模板。
- 外部运行记录绑定应用文件哈希、实际依赖及环境、输入摘要、命令/日志、结果与提交方式。人工提交结果明确为人工提交，不自动认证其真实性；内容改变使旧验证过期。
- 已审阅、待处理、待验证、已完成处置分别记录。演示负责人字段不冒充实名鉴权；模型不能批准升级。保持不执行上传代码、不自动写回的约束。

评测比较静态规则、规则+关系、再加 RAG 查证、再加受限补查的增益。分别测风险位置漏报/误报、关系候选正确性、缺口识别、回归要求适配和错误放行；某模块没有增益如实报告，不强行宣传 Agent 提升。

## 交付与停止条件

三组工作可交错推进：先冻结范围、接口与评测，再并行安排资料/表示、审查状态与报告设计；代码集成后用新的完整验证集选型，最后同步前后端发布身份。此建议不授权创建额外代理任务或部署。

完成一版后交付：范围一致的演示、可追溯升级报告、新评测结果与消融表、至少一个失败案例、真实升级回归记录、技术取舍说明。线上成绩只在实际部署策略与数据匹配后展示。

展示重点：日常指定版本查询；同一应用旧消费者的升级风险及证据路径；修复与外部回归后处置；动态关系/证据不足时保留未知项。避免只演示会成功的样例。

本轮不扩版本、不换行业、不堆框架、不追求全量上游代码分析。完成可信闭环和一次独立验证后冻结秋招版本，再决定下一轮。
