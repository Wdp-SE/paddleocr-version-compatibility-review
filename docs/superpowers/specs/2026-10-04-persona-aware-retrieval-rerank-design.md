# 面向研发角色的证据优先 RAG 与变更审查设计

## 目标

面向 AI 应用开发岗位继续打磨 PP-Human 研发知识 RAG 与变更审查 Agent，使检索策略能解释其业务适配依据，并让研发查询者和变更审核者各自更快核验关键信息。准确性、版本正确性、证据支持和关键影响漏检优先于毫秒级延迟；额外处理必须有界、可观测、可评测。

## 用户、资料与工程约束

- 主要用户是使用 PP-Human 工程资料的研发工程师，以及审阅模型、行为分析、跟踪或部署变更的技术审核者。系统按用户当前任务选择结果组织方式，不收集或推断用户身份、职级或权限。
- 当前公开语料来自 PaddlePaddle/PaddleDetection 的 PP-Human 中文 Markdown 教程和必要 YAML 配置；快照覆盖 v2.5.0 至 v2.9.0 共 6 个版本、14 个文档主题和 761 个检索片段。它是公开资料的受控快照，不代表上游全量文档或企业内部资料。
- 精确模型名、配置文件名、YAML 键和值需要词面准确匹配；中文问题和英文配置术语之间存在词汇差异；变更审查需要覆盖多个有限检查项，并避免把相关资料说成已确认影响。
- 公网 RAG API 运行在 Render 免费服务，生成模型通过服务器端 DeepSeek API 配置访问。方案不引入新的本地大模型下载或重型 reranker 依赖；实验重排会额外调用现有模型服务并增加费用。密钥仅留在服务端。
- 当前用户明确优先考虑检索和审查的准确性、真实性与可靠性，接受额外处理时间；但系统仍需有单次请求的超时、有限检索规划、阶段状态和失败回退，不能出现无界循环。
- 当前检索评测证明候选策略有来源召回收益，但没有有效 Agent HOLDOUT，也没有答案正确性、引用支持和实际影响判断的人工盲审结果。因此实验策略不得因召回指标单独晋升为默认。

## 设计原则

1. 先执行知识空间、版本、语言和来源边界过滤，再做候选生成与排序；重排不得跨越授权资料范围。
2. BM25 保持稳定基线。实验路由与模型重排可显式选择或在实验模式内自动路由，但不能在缺少独立端到端评测时替换默认策略。
3. RAG 负责返回可追溯证据；模型只可排序已检索候选并依据最终证据生成答案。模型不得发明、补写或修改候选来源。
4. 不输出未校准的置信度百分比。显示检索覆盖、引用校验、版本核对、缺口和策略执行状态等可解释信号。
5. 不修改上游资料，不自动判定真实影响，不绕过人工审核。

## 端到端流程

```text
用户任务与范围
  → 校验项目/版本/语言/来源
  → 识别任务与查询形态
  → BM25 / 中文术语扩展候选检索
  → 去重、融合并限制候选池
  → 可选模型重排（只返回已有候选 ID 的顺序）
  → 证据充分性和版本检查
  → 引用约束的 RAG 回答或变更影响候选
  → 角色适配的呈现
  → 人工核验与盲评反馈
```

### 查询与任务路由

路由使用可解释的规则，而非把用户身份发送给模型或从用户文本推断权限。

- `DIRECT_LOOKUP`：查询主要由明确模型标识、配置文件/路径、YAML 键、命令参数或版本标识构成时，以 BM25 精确词面召回为主；若同一问题还包含原理或用途描述，才补充受控术语扩展。
- `CONCEPTUAL_LOOKUP`：问题以原理、流程、适用条件或自然语言描述为主时，在 BM25 之外使用受控 PP-Human 中文术语扩展召回，以弥补中文表述与配置词之间的差异。
- `CHANGE_REVIEW`：沿用现有有限检查计划，为每个检查项检索；每个候选保留对应检查项、版本和来源元数据，避免排序后丢失某个检查维度。
- 无法稳定分类时使用 `GENERAL_LOOKUP`，同时运行 BM25 与可用的术语扩展候选并融合；UI 和 trace 暴露路由结果与策略，不暗示分类已被用户确认。

路由器只选择检索链路，不判定问题是否可回答。语料外问题由后续证据充分性检查和生成模型的结构化拒答流程处理。

### 候选生成与模型重排

- 概念型及通用知识查询为 BM25 和术语扩展各取不超过 Top-20 候选，按 chunk ID 去重后使用现有 RRF（`rrf_k=60`）融合，最终重排池最多 24 条；至少保留 BM25 前 5 条，防止术语扩展挤掉文件名或参数名。纯精确标识符查询默认只取 BM25，避免无益扩展干扰精确命中。
- 变更审查继续遵循最多 4 个规划检查项。每个检查项从 BM25 与适用的术语扩展各取不超过 Top-5；去重后的总重排池最多 40 条，并保留每条候选来自哪些检查项。最终证据集不超过现有 8 条预算，并尽量覆盖不同检查项和来源。
- 使用当前配置的生成模型执行一次批量重排调用，不为每条 Agent 子查询单独调用模型。重排输入包括原始问题/变更摘要、检查项和候选的稳定 ID、标题、路径、版本及证据摘录；单条摘录最多 600 字符，整批摘录最多 12,000 字符，超限时先在候选间平均分配预算、再按既有融合顺序分配剩余额度，并记录截断标志。提示词把文档内容视为不可信数据，忽略证据内的指令。
- 重排输出采用 `{"ranked_ids":[...]}`，只含候选 ID 且必须是输入候选的完整排列；不生成答案、不生成新证据、不改变原文、不返回相似度或置信度分数。服务端验证 ID 集合完全相同且无重复；缺失、重复、额外 ID、格式错误或超限输出均不得采用。
- 重排只用于候选排序，不将模型给出的数字当作概率或正确性评分。排序后的证据仍须通过当前版本、来源和引用成员校验。
- RAG 页面保留用户可调 Top-K（当前范围 1–20），它表示希望最多展示/送入生成的证据条数；现有生成上下文预算仍是硬上限，实际送入条数可能更少，并须向用户报告实际值。Agent 最终仍最多选取 8 条。Agent 按检查项轮转取证，先尽量给每个有候选的检查项保留一条，再按重排顺序补足，避免一个检查项占满证据预算。不给用户提供未校准的 rerank 分数阈值；证据不足由明确的充分性检查和拒答处理。
- 重排调用失败、超时或输出结构无效时，退回已验证的 BM25/RRF 排序并记录 `RERANK_FALLBACK`；如果没有有效正向证据，维持现有拒答行为。页面必须清楚标明重排是否执行、是否回退；不能静默冒充重排成功。
- 新链路每个用户请求最多增加一次重排 API 调用；Agent 的多条检索子查询批量合并后排序。此为单次流程边界，不设置用户会话累计调用次数上限；供应商费用、服务限流和请求超时仍按其自身规则生效。

### 证据充分性与生成边界

- 版本和来源过滤是硬约束；无正向检索证据时不调用回答/审查生成。
- RAG 回答继续采用逐条主张绑定证据 ID。页面优先展示短答案及对应原文，证据覆盖提示仅解释哪些查询词/检查维度尚未被证据覆盖，不是模型置信度。
- Agent 继续最多拆分 4 个检查项。每个影响候选必须绑定本次检索结果中的证据 ID；未覆盖检查项、版本歧义和模型引用校验失败作为结构化缺口展示。未检索到证据只表示资料不足，不代表没有影响。
- 引用错误或版本不符的输出继续隐藏或降级为检索线索；Reranker 不得放宽已有结构化输出验证。

### 任务适配呈现

- **研发资料查询视图**：优先展示直接答案、适用版本、文档标题/路径和逐条引用；未回答时说明证据缺口及当前语料范围。技术策略、候选列表和耗时放在可展开详情中。
- **变更审核视图**：优先展示变更摘要、检查项覆盖、影响候选、候选证据、建议验证动作、资料缺口和人工审核操作。使用“待确认影响候选”，不得使用“已影响/已确认”。
- 当前 RAG 查询页和变更审查页已经区分两种任务；本设计重排信息优先级并补充证据状态，不另造一套用户账号、角色权限或平行工作流。
- 过程进度按“范围校验、计划、检索、重排、生成”显示完成/失败/回退状态；不显示缺乏数据依据的预计剩余时间。

## 可观测性与成本

每个请求记录非敏感字段：request ID、路由标签、请求和实际检索策略、重排状态、候选数、最终证据数、检索/重排/生成阶段耗时、模型名称和供应商返回的 token 用量（若提供）、失败类别与回退原因。日志不记录密钥、完整提示词、模型响应体或完整证据正文。

RAG API 把各阶段耗时分开返回。界面报告重排是否额外调用模型，以及已知 token 用量；如果服务商未返回 token 用量，显示“未返回”，不估算金额。公网 demo 的当前资料和检索内容来自公开语料；用户输入的变更描述会沿用现有生成流程发往已配置的外部模型服务。生产企业部署前，必须另行确认数据驻留、隐私和模型供应商审批，并优先使用企业批准的私有模型端点。

## 评测与采用门槛

不再重跑已经消耗的 RAG HOLDOUT 来调策略。创建新的分层评测集，至少覆盖精确标识符查询、概念/多资料问题、版本边界、资料外问题及变更审查；案例按文档族隔离，不复用或改写现有题目。答案和影响的业务标签由 PP-Human 熟悉者先独立标注并对争议项复核，系统策略使用盲化 arm ID。

RAG 主指标为：事实主张正确率、引用支持率、版本正确率、可回答性/拒答正确率、必需来源召回和完整来源集命中。Agent 主指标为：影响候选精确率/召回率、关键影响漏检率、证据支持率、检查项覆盖。P50/P95 检索、重排与生成耗时，以及每任务 token 用量属于次要权衡指标。

预先固定采用规则：

1. 精确配置/标识符查询的事实正确率、引用支持率和版本正确率均不得低于 BM25 基线。
2. 概念及多资料查询须在独立案例上提高完整必需来源覆盖，且不得以引用支持率下降换取更多候选。
3. Agent 的关键影响漏检率不得比基线恶化；若召回提高但候选精确率或证据支持率明显下降，不晋升默认。
4. 无答案问题的拒答正确率和错误引用数不得恶化；模型重排失败回退必须在评测中计入。
5. 样本不足、评审分歧未解决或结果不确定时，保持 BM25 默认并保留实验入口，不宣布获胜策略。

评测报告分别列出任务类型和总体配对结果、评审一致性、失败案例、token 用量和分阶段延迟；不把来源召回包装成答案准确率，也不依据同一批开发题同时调参和宣称泛化。

## 非目标

- 本阶段不接入私有 Jira、GitHub 企业库、员工账号、组织权限或真实工业设备，也不声称具备企业生产部署能力。
- 不改动上游 PP-Human 项目资料，不自动提交变更，不取代研发审核。
- 不重跑或修改已使用的 HOLDOUT，不通过增加测试样例的相似改写来刷指标。
- 不添加本地大型 cross-encoder 模型依赖，不因为低检索毫秒数而选择更复杂架构。
- 不把用户画像当作个人画像或授权来源；仅按当前任务选择结果视图。

## 验收条件

1. API、RAG UI 和 Agent UI 均可显示路由标签、请求/实际策略和重排执行状态；实验选项不改变 BM25 默认。
2. 模型重排最多执行一次/用户请求，批量处理 Agent 检索候选；错误 ID、重复 ID、越界候选、空输出、超时及模型不可用均能安全回退。
3. 原有版本/来源过滤、证据成员校验、最多 4 项 Agent 计划、8 条最终证据上限和人工审核边界均有回归测试。
4. 两种任务视图分别把原文核验或影响审核所需信息放在结果主区域，展示中不出现未校准置信度或确定性影响断言。
5. 新盲评集、标注说明、评分器和配对报告可复现，并包含模型重排失败回退样例；未完成真实盲评前不能切换在线默认策略。
6. 单元与集成测试证明 UI、API、Agent 一致传递策略和诊断信息；运行手册说明额外模型调用、外部模型数据边界及回退行为。
