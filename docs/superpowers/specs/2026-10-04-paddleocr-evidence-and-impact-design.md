# PaddleOCR 证据检索与应用升级影响审查设计

日期：2026-10-04。状态：用户在数据覆盖讨论后再次要求开始修改，沿用 Native 方式；补充数据覆盖约束并进入书面实施计划阶段，尚未开始本轮产品实现。

## 1. 目标与用户

服务维护扫描文档处理应用的研发人员。人工日常查询 PaddleOCR 指定版本的参数、接口、配置和结果契约；升级时，对同一应用的调用、结果转换、JSON 消费及测试关联进行审查。RAG 同时是人工入口和审查工具的证据底座。

当前审查范围固定为 PaddleOCR v2.9.1 → v3.0.0。一个依赖、一条应用处理链做深，不引入其他领域或通用自主修改平台。三个现有片段属于同一业务的规则演示，不冒充已经集成的生产应用。

优先级依次为：版本与模块适用正确、关键风险不漏报、主张有支持、未知不误放行、证据完整、误报可解释；在这些要求满足后考虑延迟和费用。延迟是资源约束，不用任意百分比加权将严重错误抵消。

## 2. 已核查的现状与问题

- 当前官方语料为 54 条版本来源、1,545 个片段；仅有两个已收录版本，不称 v3.0.0 为上游当前最新版本。
- 已存在结构分块：表格、代码块、Python 定义和 YAML 映射保持完整。最长块约 1.6 万字符，短块长度中位数 144 字符。
- 按现有 reranker tokenizer，140 个片段正文超过 512 tokens，其中 85 个为表格；查询和特殊 token 还会占预算。这是可观测截断风险，不是所有失败的已证明唯一原因。
- 神经检索和重排当前主要使用正文，缺少完整章节、符号及模块上下文。词面分词使用中文双字和技术词，不能稳定映射用户问题到 API。
- 当前默认 BM25 内部留出完整召回 5/12，补充探针 4/6。两组样本均已被分析，不能再用作新方案的未见验收集。
- 现有指标要求指定文件和 token 同时命中；不能将它直接解释为答案准确率，也不能自动接受其他模块的同名字段。
- 静态审查逐文件进行；相关 RAG 查询只取前两个发现标题合并检索，缺少逐项查证。模型建议仅基于既有目标版契约证据；尚无完整跨文件应用影响链。
- 工作台单次编辑一个文件，后台允许最多 12 个文件；已有真实运行记录仅覆盖原创三页 OCR 与结果适配。

## 3. 选定方法及备选

选定：保留原始证据身份，增加细粒度检索视图、问题分解、分阶段检索诊断；扩展只读跨文件影响分析与受控查证；用新冻结数据比较并验收。

备选一：仅换较大的 Embedding/reranker。优点是改动少；不足是长表截断、短块失去语境及应用关系缺失仍然存在。作为检索结构改善后的实验候选，不作为本次唯一改法。

备选二：引入全量知识图谱、多 Agent 和任意代码沙箱。实现与维护成本高，超出当前任务，不能因此证明准确。本轮不采用。

借鉴依据：Sourcegraph Cody 的代码上下文检索、Onyx 的不同大小分块与上下文增强、Anthropic Contextual Retrieval 的片段上下文、OpenRewrite 的类型/调用关系与迁移步骤。厂商实验和企业报道不作为本项目的性能证据。

## 4. 项目级约束

- 保留当前工作区已有修改及历史记录，不重置、删除或暂存无关文件。
- 官方来源固定提交：v2.9.1 = 07603421c20a96bb94bb87d0c4211032527ae706；v3.0.0 = a8474288ad53c0f439c272b786c5fa6240f0cf27。
- 公开语料仍为中文文档及必要的 Python/YAML 契约；不再更换知识空间。
- 原始 sources、chunks、行号和 SHA 保持独立。任何索引增强或模型生成文字不得充当官方原文。
- 待审输入只允许相对路径显示标签和 UTF-8 文本；不按用户路径读取本机文件，不导入、不执行待审代码，不自动写回。
- 原创应用可在离线命令行运行；不在匿名公网接受任意执行请求。
- 用户应用 runtime_verified 和 uploaded_application_runtime_verified 保持 false；人审不能覆盖这两个状态。
- 保留现有最多 12 文件、每文件 50,000 字节、总计 200,000 字节、每文件 5,000 行、15,000 AST 节点、128 嵌套、100 发现及 100 缺口限制。
- 不增加会话累计生成次数上限。单任务的候选、轮次、证据和截止时间有后端限制，耗尽时说明原因并保留部分结果。
- 不把相似度、重排 logit 或同模型支持度判断称为正确概率；不宣称零幻觉或企业效益。
- 本轮实现与验收在本地；提交 main 与公网发布单独核对最新工作文件，不以旧分支 HEAD 替代。

## 5. RAG：检索视图与原文阅读分离

### 5.0 数据覆盖审计先行

按原始固定 Git tree 审计任务资料，而不是把现有 54 条来源称为全集。两棵树都未截断；v2.9.1 有 503 个 Markdown、1 个 PDF、0 个 DOCX/XLSX；v3.0.0 有 358 个 Markdown、0 个 PDF/DOCX/XLSX。Markdown 数量包含不同语言及不相关任务，不能全都算当前场景覆盖。

新增 coverage_manifest.json：逐项列出任务（调用、参数、结果、版面、表格、安装、部署、迁移、应用消费、回归）、适用版本、预期资料类别、已核验文件和明确缺口。枚举路径仅来自固定完整树，版本、blob SHA、语言和任务相关性均核对后才扩展 allowlist；不接入另一知识空间。

优先核查并补充确实在固定树中的 doc/doc_ch/inference.md、doc/doc_ch/algorithm_inference.md、docs/version3.x/deployment/obtaining_onnx_models.md、docs/version3.x/deployment/on_device_deployment.md。其他候选通过同一审计规则决定，不把所有算法训练教程默认为升级审查必需。现有 v3 旧教程排除仍保留。

应用材料单独记录来源类型 developer_original_application，不混标官方资料：一套应用的调用与转换代码、依赖配置、JSON 接口契约、设计说明、测试与升级记录。受限提交文本只在本次审查中使用，不自动进入跨用户公共知识库。

文档媒体链接单独列出；没有图片正文时明确标记 text_only/unextracted。仅在同固定仓库、来源与许可核验后才允许加入相关图片派生文字，提取结果须保留图片路径/字节哈希及核验状态。当前图片侧车为空，不能称图片信息已经可检索。

PDF/Word/Excel 按实际相关资料接入，不虚构官方办公文档；同内容的转换件不能作为独立资料数量或检索收益。历史解析组件的存在不等于当前活动库具备已验收的多格式数据。覆盖审计与提取缺口必须在页面和审查中可见，资料不完整时不得宣布影响范围检查完整。

### 5.1 派生视图

新增可重建的检索视图侧车。每个视图包含 view_id、parent_chunk_id、source_id、version、module、document_family、heading_path、symbol、原文起止行及 retrieval_text。视图指纹包含语料、构建代码、分词器与模型身份。

- Markdown 参数表：按行或少量相邻行建视图，附表头、标题及适用模块。复杂合并单元格 HTML 表不能可靠拆解时使用保守窗口并标明类型，不捏造列关系。
- Python：以类/方法、签名、参数与返回说明建立视图；超长方法按 AST 语句边界或连续行窗口细分，保留所属定义。不得只保留签名而丢掉返回契约。
- YAML：以映射路径与原始行块建立视图；不实例化自定义对象，不能解析时保留原文窗口。
- 短段落：检索文本附文档名、完整章节、模块、版本和符号；阅读时补充同版本、同源章节的必要邻段。

初版上下文以原始标题和结构元数据构造，不默认使用 LLM 生成全库摘要。技术符号、数字、代码大小写和标点保留；中文规范化不能改变官方拼写。

### 5.2 证据身份与阅读窗口

保持外部 canonical chunk_id、content 和 provenance 的现有含义。检索视图只负责找到位置；命中后回到已核验原始父块。

为命中父块增加 evidence_spans（父块内部的连续原文行段）及命中符号；多个同父块命中合并阅读窗口，不因去重丢掉另一个必需事实。span 必须从 source/parent 原文再计算，不能信任客户端或模型提供的正文。

生成、支持复核和界面精简展示使用已经校验的 spans；完整原文仍可展开。引用同时显示 canonical 来源与 span 行号。生成器不能看到视图增强文字后将它作为事实引用；旧客户端未提供 spans 时使用现有父块行为。

动态 token 预算根据实际模型 tokenizer 计算。重排读取查询、结构上下文和窗口正文；超过预算显式分窗，记录分窗/截断诊断。任何真正被截断的输入都不得显示“全文已核验”。

## 6. RAG：查询、候选及答案验证

### 6.1 查询需求

query_plan 保存原问题、明确版本、模块、符号、最多 4 个 evidence_requirements。精确 API/参数走符号通道；自然语言同时保留原问题、词面和语义候选；复合问题分解为可独立验证的需求。

可选模型只提出候选模块、术语和子问题；后端校验原问题显式版本及 API 不得改变。无模型、无效分解时保留原查询。版本/模块歧义会改变结果时需要澄清或分支展示，不静默混合。

旧/新版比较形成两个明确范围；单版本查询仍在召回之前过滤版本、语言和命名空间。一个比较请求中的合法双版本不能误计为错版，也不能将两个版本的默认值拼成一个答案。

### 6.2 候选与重排

开发实验比较候选池 40、80、120，且区分这是融合后的总预算，不将每路预算与总预算混称。最终 Top-K 沿用用户可配置范围 1–20；多问题的候选预算在需求之间分配，排序与组装记录每个需求是否有证据。

比较原 BM25、上下文/符号增强词面、语义、多路融合和结构窗口重排。候选不全时不能把重排当补救；候选充分而重排丢失时评估模型/窗口；生成阶段错误另行统计。

父块选择分数及多窗口聚合规则提前固定在开发配置中并记录；不在最终验收时改参数。同模块高度重复内容去重；不得强制跨模块多样性，也不随意剔除低分但必需的已确认契约。

提升链路不是预先指定默认。模型缺失、超时、非有限值或窗口构建失败时返回明确降级信息和原文，不把词面回退伪装成重排成功。新选型结果必须绑定当前构建，否则回到明确标记的 BM25 基线。

### 6.3 生成与机械检查

每条答案主张绑定本请求的适用版本证据。保留最多 5 条主张、60,000 字符支持复核预算及现有失败隐藏答案逻辑。

对存在结构化依据的参数名、默认值、返回字段做机械一致性检查；仅对实际引用的模块和版本检查。不能把“证据出现该字符串”当成它支持任意叙述；解释性主张仍采用模型支持复核并披露相关误差。

复合问题不能用某个子问题的有据答案掩盖其他需求未回答；部分回答明确列出缺口。未知版本、错误模块、资料无答案、生成异常、校验失败分别给具体原因。

## 7. 应用与 Agent：单一升级链做深

### 7.1 原创应用组织

增加同一个原创文档处理应用的多文件模式：OCR 调用入口、旧版结果转换、目标版适配、统一 JSON 契约、下游消费、回归测试。版面入口作为同应用的可选分支；未运行版面推理时不可借 OCR 回归宣布已验证。

现有三片段保留为规则演示/对照。工作台默认可选整套原创应用，支持最多 12 个文件的文本编辑/UTF-8 上传，上传后仍只作受限文本。避免多文件支持依赖读取任意路径或解压任意目录。

### 7.2 只读影响关系

建立提交文本内的模块/符号表和关系。支持明确 import/from-import、相对导入、简单导入别名、直接函数调用、明确返回值与字段消费者；依赖声明与 source_version 不一致时阻止“按该版本已兼容”的结论。

分离两种关系：

- reference：确实存在引用/调用，不等于运行一定可达或结果一定相同。
- result_flow：可证明的直接返回、赋值/参数传递及消费；只在受支持的表达式上推导。

动态 getattr/import、猴子补丁、条件路径、循环导入、重绑定、同名歧义、缺失文件、未知外部封装不能制造精确关系。形成带应用行号、摘录和哈希的 gap。影响路径最长 8 条边、图最多 2,000 节点和 4,000 条边；达到限制明确标记未覆盖，循环关系终止而不是递归到崩溃。

输出影响路径：上游变化依据 → 应用调用位置 → 关系链 → 消费/输出位置 → 回归要求。仅引用关系只能支持“需检查的候选”，不得升级为已经确认的业务破坏。

### 7.3 逐项查证工作流

替代前两个标题拼接查询：每个去重的发现/缺口生成一个查证项，包含 check_id、应用位置、symbol/module、所需旧/新版本证据及目标事实。

每轮最多 4 个查证项，最多 3 轮、总计 12 个查证项；每项最多分别检索一次旧版和新版，因此最多 24 次 RAG 检索调用，不能把逻辑查证项数误写为 HTTP 请求数。重复查询和已知来源读取缓存；这一限制只约束单任务，不限制会话累计使用。

模型可提出尚未解决问题的后续查询；每轮最多一次规划请求，任务最多 3 次规划请求，最终建议及其支持复核各最多一次模型请求。后端限定同知识空间、版本、允许工具和查证项，不能任意上网、下载、运行或签署。无新证据、全部需求解决、重复查询、3 轮耗尽、240 秒任务截止或用户取消时停止。每次工具调用使用剩余截止时间，已核验发现保留，失败/超时逐项解释。

静态结果和人工审核为固定可靠骨架。只有难以预先枚举的查证选项才交由模型选择，不为 Agent 命名额外增加自由循环。

### 7.4 结论级别与回归要求

- confirmed_risk：支持规则/契约、应用位置和确定关系均经校验。
- candidate：存在引用或语义关联，关系/证据不充分；模型不能写入 confirmed_risk。
- gap：未覆盖、输入不足、动态路径、查证失败等；空发现不表示兼容。
- regression_requirement：与发现或候选绑定的输入条件、目标契约、预期行为和需执行的测试。生成建议不等于测试存在/已执行。

每条模型建议绑定查证项、应用位置及允许来源，并做支持复核；支持复核失败只删除该建议，不丢弃静态报告。不把同模型判断升级成人审结论。

服务 API 兼容现有 schema_version=1；新增影响图和查证字段采用独立 impact_schema_version=1 扩展，现有消费者可忽略。图、查证和模型建议各自有状态，不能用单个 OK 覆盖部分失败。

## 8. UI、状态与工程约束

- 审查页展示应用文件列表与关系路径，报告按“确认风险／待核查候选／未覆盖／回归要求”组织。
- 输入、文件、版本、检索配置或生成选项变化均使旧报告和审阅确认失效。审计导出包含所有输入哈希、语料/策略指纹、工具轨迹、证据、关系和阶段状态。
- 原创运行记录与用户静态审查分别展示，任何覆盖率或签字不得将未执行状态改为通过。
- 长任务采用阶段进度、已处理查证项和已用时间，不虚构百分比或预计完成时间。如果需要后台任务，仅使用本次受限输入和任务状态，重启/过期要给明确状态，不宣称会话存储为企业持久审批。
- 人工接受/驳回候选保存其身份及理由；匿名演示仍不声称企业实名审核。
- 模型建议关闭时静态工具与 RAG 查证仍可工作，支持失败恢复到未解决查证项，不重复已完成请求。只读请求可按输入与构建指纹去重；不同请求不能共享应用文本。

## 9. 新评测与发布规则

### 9.1 数据与防泄漏

建立 evaluation/paddleocr_impact_v3。旧 v1/v2 问题、已看过探针及其近义改写仅为历史回归，不进入新验收。

计划的新集合：检索 30 开发、15 验证、15 最终封存题，加 12 无答案/歧义探针；审查 12 开发应用组织变体、6 最终封存应用变体，覆盖直接调用、跨文件包装、JSON 消费、配置错版和动态负对照。规模是最低实验覆盖，不称统计上充分或行业专家盲测。

同一问题的近义改写、同一代码骨架变体必须在同一分组；按任务/章节与应用组织方式分组，不能随机切片导致近重复泄漏。标注合法来源集合、适用模块/版本、必需事实和否定条件；等价证据先人工核对，不能在看到排名后放宽标签。

冻结查询、来源集合、代码及配置后才测。开发选择候选，验证选择一个配置；最终封存集仅运行一次，失败也发布并作为下一版本开发材料。不覆盖旧报告，不把自编新集称第三方盲测。

### 9.2 指标及消融

检索：候选事实召回、最终事实召回、完整回答所需证据覆盖、重排保留率、错版/错模块片段、上下文冗余、token 截断；另外保留指定来源召回，两者分开。

生成：关键事实正确与完整、逐主张原文支持、引用定位准确、错误断言、正确拒答、错误拒答、部分回答缺口。没有真实人工标签时该指标为空而不是由模型自动冒充。

审查：确认风险的正确性、已标注关键风险漏报、影响位置正确、关系级别正确、未知误判兼容、候选有效性、回归要求覆盖、阶段失败保留与恢复。

消融：A 静态规则；B 静态规则 + 应用关系；C B + RAG 查证；D C + 模型辅助。对同输入使用相同版本，分别报告新增正确项、误报、漏报、未覆盖以及成本/耗时。不能把排版改善当成推理准确提升。

候选池、结构分块、上下文增强和重排按分阶段消融；不遍历所有组合后挑最高留出成绩。新方案须在验证集提升事实完整性且不恶化关键风险/错误支持门槛，才允许成为默认。若不满足，保留可靠基线并发布失败结论。

### 9.3 回归与真实运行

重新运行服务、Agent 和工作台相关测试。重点覆盖长表末行、相同符号不同模块、双版本比较、伪造 span/来源、跨文件别名、遮蔽与缺失文件、循环关系、查证重复/超时、旧报告失效及模型关闭。

原创应用真实运行两版，以相同原创文档、输入哈希、应用/适配器哈希验证：旧消费者失败位置、适配后统一 JSON 以及下游消费回归。记录实际环境，不用 OCR 文本识别质量冒充迁移正确率；不执行任何待审上传代码。

报告绑定语料、检索视图、分词器/模型、应用关系工具、查证编排、样例和评测代码。构建变化隐藏旧成绩并解释不匹配；不得刷新哈希假装旧测试已经覆盖新代码。

## 10. 实现边界与组件责任

服务新增小模块负责派生视图/原文 span 校验、查询需求、应用关系和新版评测；与 existing public_api、paddleocr_quality、paddleocr_compatibility 集成。避免继续把所有逻辑堆入 public_api。

Agent 新增独立查证状态与编排模块，paddleocr_review 负责调用与核验；现有原文来源检查保留。

工作台新增多文件输入/影响链组件并接入现有审查页，检索配置、Top-K 及结果阅读保持现有入口。示例和评测资料分别放 examples/paddleocr_document_app 与 evaluation/paddleocr_impact_v3。

具体文件、函数、TDD 步骤及任务间接口在此设计批准后写入实施计划。延续 Native 执行方式，不重新询问方式；书面计划审核后实施。

## 11. 明确不在本轮完成的事项

不扩展其他依赖/业务领域，不自动修改公共资料，不支持任意仓库执行，不建全量企业知识图谱，不实现企业 SSO/实名签章/合规认证，不承诺全量 Python 动态分析，不声称真实客户文档验收。

本轮完成含义是实现上述受限能力、冻结并运行新实验、报告真实结果与失败、提供本地可演示版本；效果未达门槛不能以“功能已完成”代替效果验收。
